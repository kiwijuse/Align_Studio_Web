# 접근성

> 키보드 · 스크린리더 · 움직임 · 손가락

---

이 사이트는 **직접 눌러야 성립하는** 화면입니다.
그래서 누를 수 없는 사람이 생기면 사이트가 통째로 없는 것과 같습니다.

일반적인 소개 페이지라면 접근성이 떨어져도 내용은 읽힙니다.
여기는 아닙니다. 구조 자체가 상호작용이라 **접근성이 곧 기능**입니다.

---

## 1 · 보이지 않는 것이 탭에 걸렸다

첫 화면은 화면 전체를 덮는 판입니다. 그런데 **뒤에 있는 바탕화면 · 메뉴바 · 독이
여전히 탭으로 갈 수 있었습니다.**

키보드만 쓰는 사람은 보이지도 않는 항목 20여 개를 지나야 첫 화면의 버튼에 닿았습니다.
화면에는 카드 세 장뿐인데 탭을 스무 번 넘게 눌러야 하는 상태였습니다.

`inert` 를 걸어 뒤쪽 전체를 잠갔습니다.

```js
/* 세션 선택 화면은 전체를 덮는 판이다. 그런데 뒤에 있는 바탕화면·메뉴바·독은
   여전히 탭으로 갈 수 있었다. 키보드만 쓰는 사람은 보이지도 않는 항목 20여 개를
   지나야 했다. inert 를 걸면 포커스도, 클릭도, 스크린리더도 뒤로 넘어가지 않는다.
   상담 창을 게이트 위에 띄울 때는 그 창만 예외로 살려둔다. */
var GATE_BEHIND = ['#stage', '#company', '#m-menu', '.m-cta'];
```

`inert` 는 세 가지를 한 번에 막습니다 — **포커스 · 클릭 · 스크린리더**.
`tabindex="-1"` 만 걸면 탭은 막히지만 스크린리더는 여전히 읽습니다.
`aria-hidden` 만 걸면 반대가 됩니다. 둘 다 필요해서 `inert` 를 썼습니다.

상담 창을 첫 화면 **위에** 띄우는 경우가 있어서 그때는 그 창만 예외로 살려둡니다.

## 2 · 창을 열면 포커스가 따라간다

창이 떠도 키보드 포커스는 원래 자리에 남아 있었습니다.
화면에는 새 창이 떴는데 탭을 누르면 뒤쪽 어딘가로 갑니다.

열 때 창으로 옮기고 닫을 때 **원래 있던 자리로 돌려놓습니다.**

```js
lastOpener = document.activeElement;      // 어디서 열었는지 기억
w.setAttribute('tabindex', '-1');
w.focus({ preventScroll: true });

// 닫을 때
if (w.contains(document.activeElement) && lastOpener && document.contains(lastOpener)) {
  lastOpener.focus({ preventScroll: true });
}
```

`preventScroll: true` 가 중요합니다. 이게 없으면 포커스를 옮기는 순간
브라우저가 그 요소로 **스크롤을 당깁니다.** 바탕화면이 갑자기 움직입니다.

닫을 때 조건 두 개를 확인합니다.

- `w.contains(document.activeElement)` — 포커스가 아직 이 창 안에 있을 때만 되돌린다.
  사용자가 이미 다른 데로 옮겼으면 건드리지 않는다.
- `document.contains(lastOpener)` — 열었던 버튼이 아직 화면에 있을 때만.
  세션이 바뀌어 사라졌으면 되돌릴 곳이 없다.

## 3 · 손가락이 닿는 크기

WCAG 2.2 는 누를 수 있는 것의 최소 크기를 **24×24px** 로 봅니다.
모바일에서는 그보다 넉넉하게 **44px** 를 기준으로 잡았습니다.

```css
@media (max-width: 860px){
  .nx-chip, .cw-quick button, .probe-run, .sel { min-height: 44px; }
  .raw-btn   { min-height: 44px; padding: 10px 14px; }
  .hud-skip  { min-height: 44px; display: inline-flex; align-items: center; }
  #probe-id  { min-height: 44px; font-size: 16px; }   /* 16px 미만이면 iOS가 확대한다 */
}
```

마지막 줄은 접근성과 조금 다른 이야기인데 같은 자리에 있습니다.
iOS 사파리는 입력란 글씨가 16px보다 작으면 **탭하는 순간 화면을 확대합니다.**
확대된 화면은 다시 축소해야 하고 그 사이 레이아웃이 어긋납니다.

작은 글씨 하나가 화면 전체를 흔드는 셈이라 크기를 키우는 쪽이 맞습니다.

**보이는 크기를 키우지 않고 닿는 범위만 넓힌 것들도 있습니다.**

```css
.hud-skip::after,
.hud-fold::after { /* 44×32 투명 영역 */ }
```

`SKIP →` 같은 작은 글자는 크게 만들면 화면에서 튑니다.
그래서 글자는 그대로 두고 **눌리는 영역만 투명하게 넓혔습니다.**
보이는 것과 닿는 것이 꼭 같을 필요는 없습니다.

## 4 · 움직임을 줄여달라고 한 사람에게

이 사이트는 애니메이션이 많습니다. 미끄러지고, 깜빡이고, 확대되고, 무대가 열립니다.

전정기관이 예민한 사람에게는 이런 화면이 **어지럼증을 일으킵니다.**
운영체제에 "동작 줄이기"를 켜둔 사람이 그런 경우입니다.

```css
@media (prefers-reduced-motion: reduce){ ... }
```

CSS에서 다섯 군데, JS에서도 같은 값을 봅니다.

```js
if (glowDone || reduce || !isDesk()) return;
```

**끄는 게 아니라 줄입니다.** 강조 자체를 없애면 "여기를 누르세요"가 전달되지 않습니다.
깜빡임 대신 색과 테두리로 남기고 미끄러짐 대신 즉시 나타나게 합니다.
정보는 그대로 두고 **움직임만** 뺍니다.

## 5 · 지금 무슨 일이 일어났는지 알린다

화면이 바뀌었는데 화면을 못 보는 사람에게는 아무 일도 안 일어난 것과 같습니다.

```html
<div class="notif-area" id="notif-area" aria-live="polite"></div>
<div id="reveal" role="dialog" aria-live="assertive">
```

두 단계를 나눴습니다.

- `polite` — 알림 카드. 읽던 것이 끝나면 알려준다
- `assertive` — 반전 연출. 화면 전체가 바뀌었으니 **지금** 알려야 한다

전부 `assertive` 로 하면 스크린리더가 계속 말을 끊습니다.
전부 `polite` 로 하면 화면이 통째로 바뀐 것을 늦게 압니다.

문서 전체에 `aria-label` · `aria-live` · `role` 이 88군데 붙어 있습니다.

## 검사 도구가 두 번 틀렸다

접근성 검사를 직접 짜서 돌렸는데 **도구 쪽이 틀린 적이 두 번** 있었습니다.

**첫 번째.** "숨어 있는데 탭으로 닿는 요소"가 **111개** 나왔습니다.
숫자가 이상해서 들여다보니 `display:none` 인 요소까지 세고 있었습니다.
`display:none` 은 애초에 포커스 대상이 아닙니다.

실제 문제는 **29개**였고 `inert` 를 걸고 나서 **6개**가 됐습니다.

**두 번째.** 명도 대비를 계산하면서 **반투명 배경을 빼먹었습니다.**
배경이 `rgba(...)` 면 뒤에 깔린 색과 섞인 결과가 실제 색인데
지정된 값만 보고 계산했습니다.

그래서 가장 어두운 두 곳을 놓쳤습니다.

```
터미널 줄번호   1.85 : 1     (기준 4.5)
터미널 경로     4.32 : 1
```

**재는 도구부터 의심해야 한다**는 걸 두 번 배웠습니다.
숫자가 예상과 크게 다르면 화면이 아니라 자를 먼저 봐야 합니다.

> 대비를 높이려고 바꿨던 색들은 이후 **전부 되돌렸습니다.**
> 화면 전체의 톤이 무너졌기 때문입니다.
> 접근성과 디자인이 부딪힐 때 어느 쪽을 택할지는 만드는 사람의 판단이고
> 이 사이트에서는 톤을 지키는 쪽을 골랐습니다. 기록으로 남겨둡니다.

---

## 남은 것

화면 밖의 문제라 여기서 고칠 수 없는 것들입니다. 서버 쪽 설정이 필요합니다.

- `Content-Security-Policy` · `HSTS` 헤더 없음
- `Cache-Control: no-store` 가 사이트 전체에 걸려 있음
- 분석 도구와 개인정보 처리방침 문구가 서로 어긋남
